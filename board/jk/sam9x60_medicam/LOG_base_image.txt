7.15 [x] board identity implemented and verified on hardware (F24 / PLAN 8.4)
        files: fs-overlay/usr/local/sbin/medicam-identity.sh,
               fs-overlay/etc/systemd/system/medicam-identity.service,
               fs-overlay/etc/systemd/network/10-medicam-eth0.link,
               preset gains "enable medicam-identity.service",
               medicam-hostname.service now After=medicam-identity.service
        record (96 ASCII bytes at EEPROM offset 0, space padded):
          MCM1 1 mac=<12 hex> serial=<16 chars> crc=<cksum of the prefix>
        logic: valid record -> apply and stop (never rewritten, EEPROM endurance);

14.1 [x] sdcard-rescue.img COULD NOT BE WRITTEN by balenaEtcher: it hung on
        "Starting..." for >10 min with two different cards and two different
        USB-SD readers, and a PC reboot changed nothing. The card, readers and

          * the UNC path behind the mapping is not reachable directly
            (Test-Path '\\<host>\Sync\...' -> False even unelevated), and
          * an elevated process (Etcher's helper, or any "Run as administrator"
            PowerShell) has no drive mappings at all.
        Copying the image to a local disk first made Etcher write it in one pass.
        Rule for next time: stage the image on a local disk before any flashing
        tool - this is a host workflow issue, not an image issue.

14.2 [!] "/boot is empty, there is no /boot/flash_nand.sh" on a freshly booted
        rescue card. Two causes:
          * the script is named flash-nand.sh (hyphen), and
          * the card's FAT partition (mmcblk0p1) is never mounted: /etc/fstab has
            only "/dev/root / auto rw 0 1", and U-Boot reads zImage and the DTB
            from that FAT directly, so the kernel has no reason to mount it.
            /boot is an empty directory in the rootfs.

        u-boot-nand.bin, uboot-env.bin, zImage, at91-sam9x60_medicam.dtb).
        The script cannot fix this itself: its ensure_boot() runs from the very
        partition it would have to mount.

14.9 [ ] OPEN (other BSP - Maxicam board, recorded here because it served as a
        control in 13.7.5): its rootfs ships no eth0 stanza in
        /etc/network/interfaces, so DHCP is not automatic (it needs
        `ip link set eth0 up; udhcpc -i eth0` after every boot); the kernel gives
        eth0 a random MAC on every boot ("invalid hw address, using random") and
        udhcpc sends no hostname, so the router sees a new device each boot, named
        after its MAC. Worked around on that card with "auto eth0" / "iface eth0
        inet dhcp"; pinning the MAC and sending a DHCP hostname are still to do in
        that repository.
